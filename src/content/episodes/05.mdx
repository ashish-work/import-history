## The World

The timing could hardly have been worse. The financial crisis meant nobody had budget to port working code. Then the mobile boom meant everyone was building and nobody was migrating.

And yet the break was becoming unavoidable, because unicode was no longer optional: the web had gone global, emoji were coming, and `UnicodeDecodeError` was the landmine buried in every 2.x application, waiting for production traffic to find it.

## The Pressure

Python 2's original sin: `str` is bytes. Unicode lives in a separate type, and implicit coercion between them hides bugs until the worst possible moment. Around that sin, accumulated cruft — the `print` statement, integer division that truncates, classic classes.

## The Response

Python 3.0 was a considered answer to every one of those pressures: the str/bytes split, `print()` as a function, true division, iterators and views everywhere, classic classes gone. Each change was right. Together, all at once, they broke the world.

Then came the long repair, and it took twelve years. The moratorium (PEP 3003, 2009–11) froze the language so PyPy, Jython, and IronPython could catch up — a road not taken more often. 3.1 fixed io speed. PEP 404 (2011) declared, in writing, that there would be no Python 2.8 — in the PEP's own words, "It is an ex-release." 3.3 restored the `u''` prefix (PEP 414, authored by Armin Ronacher and Nick Coghlan) as an explicit peace offering, alongside PEP 393's flexible strings. 3.4 shipped pip with every install via ensurepip (PEP 453) — bundled, deliberately, rather than swallowed into the stdlib. And 3.5 finally delivered the carrots: async/await, the `@` operator, typing.

The tooling war told its own story: 2to3's one-way translation failed; six and single-source straddling won; a site called python3wos — the "wall of superpowers" — tracked which libraries had crossed.

The end came slowly, then all at once: 2.7's end-of-life was pushed five years to 2020 (announced around PyCon 2014, written into PEP 373); the final release, 2.7.18, shipped on April 20, 2020; pip 21.0 dropped 2.7 in January 2021; macOS stopped shipping it in 12.3, March 2022.

For years the schism held itself in place: users waited for libraries, libraries waited for users. The chicken-and-egg deadlock threads repeat like a chorus.

## Why Your Code Looks Like This

Why are `b''` and `.encode()`/`.decode()` everywhere? Because the str/bytes split is the schism's monument. Why does `print` have parentheses? You know why now.

But the deepest mark is cultural: deprecation in Python is now glacial, `from __future__` is a way of life, and the community carries a permanent trauma — never again a big-bang break. It's why Guido frames it as "there will never be a Python 4." Other languages carry the same scars from the same era: PHP 6, Perl 6 — the one that had to become a different language named Raku.

How long did the schism actually last? As late as 2019 — eleven years after 3.0 — [JetBrains' developer survey](https://www.jetbrains.com/lp/python-developers-survey-2019/) still found 10% of Python developers actively using Python 2.
